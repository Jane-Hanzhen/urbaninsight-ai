# Data Specification

## Overview

UrbanInsight AI uses a lightweight SQLite database as the application's primary data source.

The platform follows an **Analysis Engine + AI Decision Agent** architecture.

Raw urban indicator data is stored in a CSV file and imported into SQLite through an explicit Python script.

The web application never reads the CSV or SQLite directly.

## Public repository distribution

The private CSV and canonical geographic working copy remain excluded from Git:

- `data/london_indicators.csv`
- `data/london_boroughs.geojson`

The processed indicator CSV is private analytical data and is injected during
deployment. The London borough boundary GeoJSON is prepared from
[`radoi90/housequest-data`](https://github.com/radoi90/housequest-data), whose
repository publishes it under the MIT licence. The upstream copyright and licence
notice must be retained when the boundary is redistributed. Third-party data is not
covered by the project software licence.

The attributed browser copy is tracked at
`public/data/london_boroughs.geojson` together with
`public/data/LICENSE.housequest-data.txt`.

The Analysis Engine and AI Context Builder read SQLite through the backend repository layer.

SQLite is the single source of truth for runtime borough, indicator and analysis data.

# Database

SQLite is used as the embedded database.

No external database server is required.

The default file is:

```text
backend/urban_insight.db
```

The schema is initialized automatically during FastAPI startup and by data scripts.

Schema initialization does not import the CSV and does not run analysis.

# Database Schema

## Table: boroughs

Stores basic information for each borough.

Fields

| Field | Type | Constraints |
|---|---|---|
| `id` | TEXT | Primary key; LAD code |
| `name` | TEXT | Required; unique |
| `region` | TEXT | Required |
| `geometry_reference` | TEXT | Optional |
| `created_at` | TEXT | Defaults to current timestamp |

An index is created on `name`.

The importer stores geometry references in this format:

```text
/data/london_boroughs.geojson#Camden
```

---

## Table: indicators

Each row represents one borough.

| Field | Type | Dimension |
|---|---|---|
| `borough_id` | TEXT | Primary key and foreign key |
| `gdhi_per_head_gbp` | REAL | Economic |
| `business_density_per_1000` | REAL | Economic |
| `house_price_earnings_ratio_reverse` | REAL | Economic |
| `police_mean` | REAL | Social |
| `convenient_service_mean` | REAL | Social |
| `cultural_mean` | REAL | Social |
| `medical_mean` | REAL | Social |
| `bus_mean` | REAL | Social |
| `ndvi_mean` | REAL | Ecological |
| `wet_mean` | REAL | Ecological |
| `landscape_index` | REAL | Ecological |
| `household_waste_recycling_rate_pct` | REAL | Ecological |
| `updated_at` | TEXT | Current timestamp |

All 12 indicator values are required.

`borough_id` references `boroughs.id` with cascade deletion.

The source typo `meandical_mean` is normalized to `medical_mean`.

The source field `bus_new_mean` is normalized to `bus_mean`.

---

## Table: analysis_results

Stores statistical results generated by the Analysis Engine.

| Field | Type | Description |
|---|---|---|
| `borough_id` | TEXT | Primary key and foreign key |
| `overall_score` | REAL | TOPSIS closeness score multiplied by 100 |
| `regional_rank` | INTEGER | Ordinal London rank |
| `economic_score` | REAL | Economic TOPSIS score |
| `social_score` | REAL | Social TOPSIS score |
| `ecological_score` | REAL | Ecological TOPSIS score |
| `contribution_json` | TEXT | Serialized contribution and PCA metadata |
| `updated_at` | TEXT | Current timestamp |

`contribution_json` has this structure:

```json
{
  "dimensions": {
    "Economic": 0,
    "Social": 0,
    "Ecological": 0
  },
  "indicators": {},
  "weights": {},
  "pca": {
    "components": 0,
    "explained_variance_ratio": [],
    "cumulative_explained_variance": 0
  }
}
```

Dimension and indicator contribution percentages sum to approximately 100 for each borough.

# CSV Import

The reusable import script is:

```text
backend/scripts/import_data.py
```

Default command from the project root:

```bash
backend/.venv/bin/python backend/scripts/import_data.py
```

Optional paths:

```bash
backend/.venv/bin/python backend/scripts/import_data.py \
  --csv data/london_indicators.csv \
  --database backend/urban_insight.db
```

The import process:

- Opens the CSV with `utf-8-sig`
- Requires the exact inspected column order
- Trims borough identity fields
- Removes commas and surrounding whitespace from numeric values
- Rejects empty or non-numeric indicator values
- Rejects duplicate LAD codes in one import
- Upserts borough records by LAD code
- Upserts indicator records by borough ID
- Updates indicator timestamps on conflict

The import is repeatable and does not create duplicate boroughs.

It does not delete database boroughs that are absent from a later CSV.

# Analysis Engine

The Analysis Engine is implemented in:

```text
backend/analysis/engine.py
```

Default command:

```bash
backend/.venv/bin/python backend/scripts/run_analysis.py
```

Processing steps:

1. Read all 12 indicator columns ordered by borough ID
2. Require at least two borough rows
3. Reject missing, non-finite or constant indicator columns
4. Standardize each indicator with population standard deviation
5. Fit PCA using NumPy singular value decomposition
6. Retain enough components to reach at least 85% cumulative explained variance
7. Derive non-negative indicator weights from absolute loadings and explained variance
8. Min-max scale indicators
9. Run weighted TOPSIS
10. Multiply scores by 100
11. Assign stable ordinal ranks
12. Run separate TOPSIS evaluations for the three dimensions
13. Calculate borough-specific indicator and dimension contributions
14. Upsert results into `analysis_results`
15. Delete stale analysis rows not present in the current run

All indicators are treated as benefit-oriented inputs.

Any cost-oriented source transformation must occur before analysis.

The house-price field is already supplied as a reversed indicator.

# AI Data Access

The AI Decision Agent never accesses raw CSV files.

The Context Builder retrieves:

- Borough ID, name and region
- Overall score
- Regional ranking
- Economic score
- Social score
- Ecological score
- All 12 indicator values
- Dimension contributions
- Indicator contributions
- PCA weights
- PCA metadata
- TOPSIS score and rank

Missing boroughs, indicators or analysis results cause context construction to fail.

The AI uses structured context to interpret results.

It never performs statistical computation.

# Dashboard Data Flow

When a user selects a borough:

1. Resolve the borough name to its API ID
2. Request indicator values
3. Request stored analysis results
4. Post an AI analysis request
5. Render scores and charts from the stored analysis
6. Render strengths, weaknesses and recommendations from `AnalysisInsights`

The statistical requests and AI request run independently.

The workspace displays a localized preview profile if stored analysis cannot be loaded.
